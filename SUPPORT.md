# Support Guide

Code contributions are not currently accepted; suggestions, bug reports, and
comments are welcome.

This guide explains how to file feedback that maintainers can act on quickly.
Issue forms are the only gateway for community interaction: every published
repository accepts bug reports and suggestions through its issue forms.

## Where to file feedback

Use the issue tracker of the affected repository. If you are unsure where a
report belongs, open it in the repository closest to the behavior you
observed.

- **Bug reports** — reproducible defects in any published component.
- **Suggestions** — feature ideas, improvements, and ideas for the preset
  catalog.
- **Comments** — feedback on issues, plans, and documentation.

Security-sensitive reports must follow the [security policy](./SECURITY.md)
instead of public issue filing.

## Reporting a good bug report

A good bug report states:

- **Component version** — the release version or the commit hash where the
  defect occurs.
- **Operating environment** — Linux distribution and version, desktop
  environment, and display server (Wayland or X11).
- **Reproduction steps** — precise sequential instructions a maintainer can
  follow to observe the defect.
- **Expected vs. actual behavior** — what should have happened versus what
  actually happened.
- **Diagnostic logs** — relevant terminal traces, `journalctl` output, or
  console errors, attached where possible.

## Writing an effective suggestion

Describe the problem you are trying to solve before the solution you have in
mind. Suggestions that name the affected family workflow, the component, and
the acceptance criteria are the easiest to act on.

## What happens next

Maintainers evaluate feedback against the project's working agreements and
respond on the issue. When a suggestion cannot be accepted, expect an
explanation of why so the underlying need can be addressed another way. Be
kind and precise — see the [code of conduct](./CODE_OF_CONDUCT.md).
